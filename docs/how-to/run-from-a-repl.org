#+TITLE: How to run a Shiso app from a REPL
#+OPTIONS: toc:2 num:nil

*Development* uses a persistent REPL and =start-server= from the
scaffolded =src/main.lisp=. =make && ./myapp= is for *deploy* (and
occasional production smoke tests), not the day-to-day edit loop.

* From SLIME or SLY

In Emacs:

#+begin_src lisp
;; Open M-x slime  (or sly)
;; Ensure ASDF sees the project (load build.lisp once from the project root, or register the tree)
(asdf:load-system :myapp)
(myapp:start-server)       ; setup-database + shiso:start
;; Edit src/modules/.../controllers.lisp
;; C-c C-c on the changed defun re-installs it
;; Reload the page in your browser — the new code is live
(myapp:stop-server)
#+end_src

=myapp:start-server= /must/ set up the database (Mito connection +
table ensures) before calling =shiso:start=. The scaffolded
=main.lisp= puts that wiring in =start-server=, so just calling it is
enough. Host, port, and debug come from =config= / the environment.

* From the cl-mcp REPL or any other bare REPL

Same idea, but without an editor integration:

#+begin_src lisp
(asdf:load-system :myapp)
(myapp:start-server)
;; Edit a file on disk
(load "src/modules/myapp/controllers.lisp")    ; or asdf:load-system :myapp/module :force t
;; Reload the page
(myapp:stop-server)
#+end_src

For an entire module's worth of edits, force a recompile of the
module system rather than =load=-ing files one at a time:

#+begin_src lisp
(asdf:load-system :polls/module :force t)
#+end_src

The =:force t= flag tells ASDF to recompile and reload even if its
timestamp tracking says nothing changed (which it sometimes doesn't,
especially across editor saves and ASDF cache).

* Pitfalls

** Class redefinition

Editing a =define-model= form and reloading does /not/ migrate the
database schema. Old rows have the old schema; new rows have the
new one. For a true rebuild, restart the server, delete the SQLite
file (or use =:memory:=), and re-run =setup-database=.

** Stale FASLs

If you've installed Shiso system-wide and then edit it in a
working tree, ASDF will still resolve to the installed version
unless you explicitly point its source registry at the working
copy:

#+begin_src lisp
(asdf:initialize-source-registry
  '(:source-registry
    (:directory "/Users/you/code/shiso/")
    :inherit-configuration))
(asdf:load-system :shiso :force t)
#+end_src

After that, =asdf:system-source-file= reflects the working tree:

#+begin_src lisp
(asdf:system-source-file (asdf:find-system :shiso))
;; => #P"/Users/you/code/shiso/shiso.asd"
#+end_src

** The Lack/Woo debugger hangs the worker

When you call =(shiso:start app :debugp t)= and a request errors,
Woo invokes the debugger on the worker thread. With SLIME attached
this is great — you get a stack-walking debugger. Without SLIME,
the worker blocks waiting for input and the server stops
responding. Pass =:debugp nil= in headless REPLs.

** Re-evaluating =define-application=

=define-application= produces a Lack-builder pipeline at expansion
time. Re-evaluating the form replaces the application value but does
/not/ kill the running server. To pick up a new mount list you have
to =(myapp:stop-server)= and =(myapp:start-server)= around the edit.

Re-evaluating =define-module=, on the other hand, takes effect
immediately — the registry is consulted at dispatch time.
